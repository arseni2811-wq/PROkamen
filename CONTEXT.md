# Контекст проекта

## 1. Назначение проекта

Система объединяет публичный сайт компании «ПРО Камень» и внутреннюю CRM. Публичная часть представляет услуги, материалы, цены, контакты и выполненные работы. CRM предназначена для авторизации сотрудников, учета клиентов и заказов, расчета стоимости изделий, контроля этапов производства, хранения вложений и формирования PDF-коммерческого предложения.

## 2. Текущее состояние

В коде реализованы публичные страницы и CRM-интерфейсы, Express API, подключение MySQL, JWT-аутентификация, ролевые проверки отдельных операций, валидация запросов, канбан заказов, карточка заказа, клиентская база, производство, архив, справочники материалов и услуг, системный курс валют, вложения, журнал действий и PDF-генерация.

Сервер проходит автоматизированный контур: 48 unit/regression/security тестов, синтаксическую проверку, миграции на пустой и legacy MySQL и сквозной HTTP-сценарий на отдельной временной БД. Рабочая БД при разработке калькулятора не изменялась.

## 3. Архитектура

- `backend/server.js` создает единое Express-приложение: подключает middleware и API, раздает `public/`, публикует `/uploads` и выполняет часть миграций при старте.
- API разделен на `routes` и `controllers`; общие проверки находятся в `middleware`.
- Контроллер заказов выполняет транзакционные операции с заказом, клиентом, позициями, финансами и журналом действий.
- MySQL используется через общий пул `backend/db.js`.
- CRM вызывает REST API через единый клиент `public/crm/crm/js/api.js`; JWT передается cookie или заголовком Bearer.
- Генерация PDF вынесена из основного потока Node.js в `backend/workers/pdf.worker.js`.
- Публичный сайт получает основной контент из JSON/CSV. Публичный калькулятор и технический калькулятор CRM получают материалы, форматы и тарифы из MySQL и выполняют расчёт только через `backend/services/calculatorService.js`.
- PHP-файлы сохранены в публичной части, но Node-сервер блокирует `/php`, чтобы не раскрывать их как статические файлы.

## 4. Технологический стек

- JavaScript, HTML5, CSS3.
- Node.js, Express 5, CommonJS.
- MySQL, `mysql2/promise`.
- JWT, bcrypt, cookie-parser, CORS.
- Zod для серверной валидации.
- Multer для вложений; PDFKit и worker threads для PDF.
- Tailwind CSS и `html2pdf.js` подключаются в CRM через CDN.
- JSON, CSV и `localStorage` используются публичной частью и клиентскими черновиками.
- PHP-обработчики присутствуют, но не исполняются Node-сервером.

## 5. Структура проекта

- `backend/server.js` — сервер, маршрутизация, статика, стартовые изменения схемы.
- `backend/db.js` — пул MySQL.
- `backend/routes/` — auth, orders, clients, materials, services, settings.
- `backend/controllers/` — обработка аутентификации и предметных операций.
- `backend/middleware/` — JWT, роли, Zod-схемы и обработчик валидации.
- `backend/utils/` — допустимые статусы и их начальное заполнение.
- `backend/workers/pdf.worker.js` — формирование PDF-коммерческого предложения.
- `backend/migrations/001_baseline.sql` — полная схема чистой БД; последующие `NNN_*.sql` учитываются в `schema_migrations`.
- `backend/scripts/` — migration runner и воспроизводимые migration/integration/integrity checks.
- `backend/uploads/orders/` — загруженные файлы заказов, если каталог создан.
- `public/index.html`, `public/pages/` — публичные страницы.
- `public/js/`, `public/css/` — логика и стили публичного сайта.
- `public/assets/data/`, `public/assets/images/` — контент и изображения.
- `public/crm/crm/` — HTML-экраны и JavaScript CRM.
- `public/php/` — PHP-обработчики, отключенные при запуске через Express.

## 6. Потоки данных

1. Публичная страница загружает `content.json`, `catalog.json`, `works.json` или `price.csv`, проверяет/преобразует данные и формирует DOM; JSON может кэшироваться в браузере.
2. Пользователь CRM отправляет логин на `POST /api/login`; сервер проверяет bcrypt-хеш в `users`, возвращает пользователя и JWT. Клиент хранит пользовательские данные и токен в `localStorage`, а сервер также поддерживает cookie.
3. CRM вызывает `/api/orders`, `/api/clients`, `/api/materials`, `/api/services` и `/api/exchange-rate`. Middleware проверяет JWT, роль, принадлежность заказа и тело запроса.
4. Создание или изменение заказа объединяет данные клиента, заказа, позиций, финансового снимка и журнала действий в MySQL; операции записи заказа выполняются транзакционно. Создание поддерживает `Idempotency-Key` в пределах пользователя.
5. Изменение заказа, калькулятора или статуса требует текущую `version`; успешная запись увеличивает её, устаревшая возвращает `409`. Канбан и производственный экран перечитывают данные через API.
6. Вложения сохраняются в `backend/uploads/orders/<order_id>/`, а метаданные — в `order_attachments`.
7. Запрос PDF читает заказ и клиента из MySQL, передает сохранённый снимок расчёта worker-потоку и возвращает клиентскую BYN-версию PDF без внутренних USD-ставок и резерва.
8. Публичный и внутренний калькуляторы передают конфигурацию в `/api/.../calculator/preview`; сервер загружает опубликованную версию прайса, рассчитывает результат и возвращает публичную либо техническую проекцию.

## 7. Основные сущности

- Пользователь (`users`) и роль (`role_id`: 1 — администратор, 2 — менеджер, 3 — работник).
- Клиент (`clients`): ФИО, телефон, email, адрес, социальные сети и источник.
- Заказ (`orders`): клиент, менеджер, статус, сумма, предоплата, адрес монтажа, источник, камень, тип изделия, сроки, курс и снимок калькуляции.
- Позиция заказа (`order_items`) и материал (`materials`, `dict_material_types`).
- Статус заказа (`dict_order_statuses`) и журнал (`order_history_log`).
- Финансы заказа (`order_finances`) и системные настройки (`system_settings`).
- Услуга (`dict_services`).
- Вложение заказа (`order_attachments`).
- Публичные сущности каталога, портфолио и контента представлены JSON/CSV-файлами.
- Прайс калькулятора (`calculator_pricebooks`, `calculator_rates`, `calculator_settings`), форматы слэбов и история изменений.
- Публичные заявки калькулятора (`public_calculator_leads`) с конфигурацией и внутренним снимком расчёта.

## 8. Основные функции

- Просмотр публичных страниц, каталога, работ, цен и контактов.
- Вход/выход сотрудников.
- Просмотр, поиск, создание и редактирование заказов.
- Перемещение заказов между этапами на канбан-доске.
- Публичный расчёт цены «от» и отправка заявки без раскрытия USD, резерва и построчных ставок; клиент видит только агрегаты материала и всех работ.
- Технический расчёт нескольких изделий, ручного расхода слэбов, операций, дополнительных строк и менеджерской корректировки.
- Версионирование прайса, редактирование ставок/коэффициентов/материалов/форматов и публикация новой версии администратором.
- Сохранение неизменяемого снимка schema v2 в заказе с поддержкой legacy-снимков.
- Ведение клиента, финансов, предоплаты и графика сроков в карточке заказа.
- Просмотр клиентской базы с агрегатами.
- Производственный экран и архив завершенных/отмененных заказов.
- Управление материалами, услугами и курсом валют с учетом роли.
- Загрузка файлов, просмотр истории и скачивание PDF.

## 9. Важные технические решения

- Frontend не требует сборки: Express напрямую раздает `public/`.
- API заказов монтируется строго на `/api/orders`; порядок `/api/health` важен из-за динамического маршрута `/:id`.
- Неизвестные API-пути возвращают JSON 404, а запросы к отсутствующим ресурсам с расширением не подменяются HTML.
- JWT принимается двумя способами: Bearer-заголовок и cookie.
- Серверная Zod-валидация используется для мутирующих маршрутов.
- Денежные значения финансовой таблицы переводятся в целые центы; в основной таблице заказа суммы остаются `DECIMAL`.
- Снимки калькуляции и дедлайны допускают JSON из MySQL или сериализованную строку.
- Список корректных статусов централизован, но фактический переход между любыми корректными статусами разрешен; отмена разрешена из любого статуса.
- Объектная авторизация централизована: admin видит все заказы, manager — только назначенные ему, worker — только безопасную производственную проекцию `/api/orders/production`.
- Технический UI поддерживает несколько изделий; calculator endpoint для schema v2 явно пересоздаёт соответствующие `order_items` внутри одной транзакции. Legacy-снимок по-прежнему использует старый single-item контракт и возвращает `409` при неоднозначном multi-item заказе.
- Часть legacy-схемы всё ещё проверяется при старте, но новые обязательные изменения применяются только versioned migration runner; старт отказывается работать без `orders.version` и `order_idempotency`.

## 10. Ограничения

- На локальной рабочей БД применены миграции 001–006 и импортирован каталог калькулятора; перед изменением схемы создана SQL-копия. Для других окружений rollout по `CALCULATOR.md` остаётся обязательным.
- Импорт `catalog.json` намеренно не придумывает закупочные цены: материалы с нулевой базовой ценой не публикуются, пока администратор не заполнит USD-цену и не подтвердит публичную доступность.
- Публичный калькулятор использует визуальный сценарий без ручных производственных метров: формы, размеры, материал, кромка, открытые торцы и понятная комплектация. Раскрой, кромка, стыки и монтаж выводятся сервером автоматически; скинали учитывает высоту и площадь, доступна предварительная раскладка по слэбу и сравнение материалов. Публичный API не возвращает отдельные цены операций; на мобильной ширине нет горизонтальной прокрутки.
- Для `order_idempotency` пока не определена политика retention/очистки старых ключей.
- В рабочей БД read-only диагностикой найдены 4 заказа без finance row и 2 несовпадения; backfill требует backup и утверждения источника истины.
- PHP-форма и Express-приложение не образуют единый исполняемый поток: `/php` заблокирован Node-сервером.
- CRM зависит от CDN-ресурсов; офлайн-режим интерфейса не определен.
- Настроенный Git remote не совпадает с указанным для диплома URL репозитория `PROkamen`; корректный удаленный репозиторий требует проверки.

## 11. Интерфейс

Публичная часть включает главную страницу, каталог, услуги, работы, сведения о компании, контакты, цены, визитку и страницу 404. CRM включает экран входа, канбан-доску, карточку заказа, калькулятор, клиентскую базу, производственный экран, архив и административную панель. Основная CRM-навигация и доступность отдельных элементов зависят от роли пользователя; окончательная матрица прав интерфейса отдельно не документирована.

## 12. Запуск проекта

```bash
cd backend
npm ci
npm start
```

Перед запуском нужны MySQL и `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_DATABASE`, `JWT_SECRET`. Чистая БД разворачивается командой `ALLOW_SCHEMA_MIGRATIONS=1 npm run migrate`; затем `npm start`. Существующая немигрированная схема требует отдельного осознанного `ALLOW_BASELINE_ADOPTION=1 npm run migrate:adopt-baseline`, после чего запускается обычный migration runner. Полная проверка: `npm run verify:full`.

## 13. Текущая область работы

Реализована единая система калькуляции: pricebook v1 в миграции 005, ручный материал в 006, чистое серверное ядро, публичный и менеджерский интерфейсы, административный черновик/публикация, schema v2 заказа и PDF по снимку. Публичная страница приведена к дизайну основного сайта и визуальному сценарию выбора; технологические количества рассчитываются сервером автоматически. Рабочая БД мигрирована и каталог импортирован.
